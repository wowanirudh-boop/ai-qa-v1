# Data Contracts

These are the canonical v1 JSON data contracts. Implementations may use Python types internally, but persisted artifacts must conform to these contracts.

Conservative v1 assumptions:

- IDs are stable strings generated by deterministic code.
- Timestamps use ISO 8601 strings when present.
- Artifact paths are relative to `artifacts/{project_id}/{run_id}/` unless a component spec says otherwise.
- Unknown fields should be rejected by schema validation unless explicitly documented as `metadata`.

## 1. ProjectConfig

Purpose: Defines the project, chatbot target, and policy settings for a run.

Required fields:

- `project_id`: stable project identifier.
- `bot_name`: chatbot or assistant name.
- `target_url`: target environment URL.
- `coverage_policy`: coverage expectations.
- `approval_policy`: approval and export gate settings.

Optional fields:

- `description`
- `source_paths`
- `artifact_root`
- `metadata`

Validation rules:

- `project_id` is required.
- `bot_name` is required.
- `target_url` is required.
- `coverage_policy` is required.
- `approval_policy` is required.

V1 note:

- Executor capability policy is deferred/future and is not a required C10 data contract. C10 obligation planning uses `ProjectConfig.coverage_policy` only unless a future data contract explicitly defines executor capability policy.

JSON example:

```json
{
  "project_id": "demo_chatbot",
  "bot_name": "Demo Support Bot",
  "target_url": "https://example.test/chat",
  "coverage_policy": {
    "require_positive_tests": true,
    "require_negative_tests": true
  },
  "approval_policy": {
    "require_human_approval_for_inferred": true,
    "allow_export_without_review": false
  },
  "source_paths": ["examples/demo_project/docs"]
}
```

## 2. Document

Purpose: Represents an ingested source document before chunking.

Required fields:

- `document_id`
- `project_id`
- `source_path`
- `title`
- `content_checksum`
- `ingestion_status`

Optional fields:

- `content_type`
- `size_bytes`
- `metadata`

Validation rules:

- `document_id` must be unique within a project.
- `content_checksum` must describe the ingested content, not only the file path.
- `ingestion_status` should be one of `loaded`, `skipped`, or `failed`.

JSON example:

```json
{
  "document_id": "doc_001",
  "project_id": "demo_chatbot",
  "source_path": "examples/demo_project/docs/requirements.md",
  "title": "Requirements",
  "content_checksum": "sha256:abc123",
  "ingestion_status": "loaded",
  "content_type": "text/markdown"
}
```

## 3. SourceRef

Purpose: Points an artifact back to source evidence.

Required fields:

- `document_id`

Optional fields:

- `chunk_id`
- `location`
- `quote`

Validation rules:

- `document_id` is required.
- `chunk_id` is required for source-derived artifacts.
- `location` is optional.

JSON example:

```json
{
  "document_id": "doc_001",
  "chunk_id": "chunk_001",
  "location": "requirements.md#payments",
  "quote": "The bot must collect an order number before showing order status."
}
```

## 4. SourceChunk

Purpose: Represents a testable or contextual slice of a source document.

Required fields:

- `chunk_id`
- `document_id`
- `text`
- `checksum`
- `processing_status`

Optional fields:

- `sequence`
- `location`
- `metadata`

Validation rules:

- `chunk_id` is required.
- `document_id` is required.
- `text` is required.
- `checksum` is required.
- `processing_status` must be one of `not_processed`, `requirements_extracted`, `non_testable_context`, `duplicate`, `out_of_scope`, `unclear`, or `failed_processing`.

JSON example:

```json
{
  "chunk_id": "chunk_001",
  "document_id": "doc_001",
  "sequence": 1,
  "text": "The bot must collect an order number before showing order status.",
  "checksum": "sha256:def456",
  "processing_status": "not_processed",
  "location": "requirements.md:12"
}
```

## 5. SourcePackage

Purpose: Groups source documents and chunks for requirement extraction.

Required fields:

- `source_package_id`
- `project_id`
- `document_ids`
- `chunks`
- `checksum`

Optional fields:

- `created_at`
- `metadata`

Validation rules:

- `document_ids` cannot be empty.
- `chunks` cannot be empty when extraction is expected.
- Every chunk must reference a document in `document_ids`.

JSON example:

```json
{
  "source_package_id": "source_pkg_001",
  "project_id": "demo_chatbot",
  "document_ids": ["doc_001"],
  "chunks": [
    {
      "chunk_id": "chunk_001",
      "document_id": "doc_001",
      "text": "The bot must collect an order number before showing order status.",
      "checksum": "sha256:def456",
      "processing_status": "not_processed"
    }
  ],
  "checksum": "sha256:pkg001"
}
```

## 6. CandidateRequirement

Purpose: Captures a possible requirement extracted from source chunks.

Required fields:

- `candidate_id`
- `statement`
- `requirement_type_guess`
- `source_refs`
- `confidence`

Optional fields:

- `rationale`
- `metadata`

Validation rules:

- `candidate_id` is required.
- `statement` is required.
- `requirement_type_guess` is required.
- `source_refs` is required and cannot be empty.
- `confidence` must be between 0 and 1.

JSON example:

```json
{
  "candidate_id": "cand_001",
  "statement": "The bot must ask for an order number before providing order status.",
  "requirement_type_guess": "functional",
  "source_refs": [
    {
      "document_id": "doc_001",
      "chunk_id": "chunk_001"
    }
  ],
  "confidence": 0.91
}
```

## 7. CandidateRequirementPackage

Purpose: Groups extracted candidate requirements from a source package.

Required fields:

- `candidate_package_id`
- `project_id`
- `source_package_id`
- `candidates`

Optional fields:

- `chunk_extraction_results`
- `skill_run_ids`
- `metadata`

Validation rules:

- Every candidate must have at least one entry in `source_refs`.
- `source_package_id` must point to the source package used for extraction.
- Candidate IDs must be unique within the package.
- `chunk_extraction_results`, when present, records chunk-level C07 extraction outcomes.
- Every chunk extraction result must include `chunk_id`, `processing_status`, and `candidate_ids`.
- Chunk extraction result `processing_status` must be one of `requirements_extracted`, `non_testable_context`, `duplicate`, `out_of_scope`, `unclear`, or `failed_processing`.
- Chunk extraction result `candidate_ids` may be empty for statuses that produce no candidates.
- Chunk extraction results may include optional `rationale` and `error_message`.

JSON example:

```json
{
  "candidate_package_id": "cand_pkg_001",
  "project_id": "demo_chatbot",
  "source_package_id": "source_pkg_001",
  "candidates": [
    {
      "candidate_id": "cand_001",
      "statement": "The bot must ask for an order number before providing order status.",
      "requirement_type_guess": "functional",
      "source_refs": [
        {
          "document_id": "doc_001",
          "chunk_id": "chunk_001"
        }
      ],
      "confidence": 0.91
    }
  ],
  "chunk_extraction_results": [
    {
      "chunk_id": "chunk_001",
      "processing_status": "requirements_extracted",
      "candidate_ids": ["cand_001"]
    },
    {
      "chunk_id": "chunk_002",
      "processing_status": "non_testable_context",
      "candidate_ids": [],
      "rationale": "Background information with no testable bot behavior."
    }
  ],
  "skill_run_ids": ["skill_run_001"]
}
```

## 8. AtomicRequirement

Purpose: Represents one normalized, independently testable requirement.

Required fields:

- `requirement_id`
- `statement`
- `requirement_type`
- `status`
- `origin`

Optional fields:

- `source_refs`
- `candidate_ids`
- `approval_required`
- `approval_status`
- `duplicate_of`
- `conflicts_with`
- `rationale`
- `metadata`

Validation rules:

- `requirement_id` is required.
- `statement` is required.
- `requirement_type` is required.
- `status` must be one of `candidate`, `atomic_draft`, `validated`, `duplicate`, `conflicting`, `needs_clarification`, `inferred`, `out_of_scope`, or `rejected`.
- `origin` must be one of `source_derived`, `inferred`, `assumption`, `user_added`, or `system_default`.
- `status` represents lifecycle or governance state.
- `origin` represents provenance.
- Origin values must not be confused with status values.
- Do not add `assumption`, `user_added`, or `system_default` to the status enum.
- If `status` is `inferred`, it is a lifecycle state for inferred requirements that have not yet been validated, and should only be used with `origin` set to `inferred`.
- Source-derived requirements must have `source_refs`.
- Source-derived requirements must have non-empty `candidate_ids`.
- Validated source-derived requirements must have non-empty `source_refs`.
- Requirements with `origin` set to `inferred`, `assumption`, `user_added`, or `system_default` may lack `source_refs`, but must require approval before export.
- Conflicting requirements cannot generate normal exportable obligations.
- Rejected requirements cannot generate obligations.

JSON example:

```json
{
  "requirement_id": "req_001",
  "statement": "The bot asks for an order number before providing order status.",
  "requirement_type": "functional",
  "status": "validated",
  "origin": "source_derived",
  "candidate_ids": ["cand_001"],
  "source_refs": [
    {
      "document_id": "doc_001",
      "chunk_id": "chunk_001"
    }
  ]
}
```

## 9. AtomicRequirementLedger

Purpose: Stores the normalized requirements produced by atomization.

Required fields:

- `atomic_ledger_id`
- `project_id`
- `candidate_package_id`
- `requirements`

Optional fields:

- `skill_run_ids`
- `metadata`

Validation rules:

- Requirement IDs must be unique.
- Source-derived requirements must preserve source references from their candidates.
- The ledger must not contain generated test obligations or test cases.

JSON example:

```json
{
  "atomic_ledger_id": "atomic_ledger_001",
  "project_id": "demo_chatbot",
  "candidate_package_id": "cand_pkg_001",
  "requirements": [
    {
      "requirement_id": "req_001",
      "statement": "The bot asks for an order number before providing order status.",
      "requirement_type": "functional",
      "status": "atomic_draft",
      "origin": "source_derived",
      "candidate_ids": ["cand_001"],
      "source_refs": [
        {
          "document_id": "doc_001",
          "chunk_id": "chunk_001"
        }
      ]
    }
  ]
}
```

## 10. GovernedRequirementLedger

Purpose: Stores final requirement governance decisions before obligation planning.

Required fields:

- `governed_ledger_id`
- `project_id`
- `atomic_ledger_id`
- `requirements`
- `governance_summary`

Optional fields:

- `policy_version`
- `skill_run_ids`
- `metadata`

Validation rules:

- Requirements marked `validated` must be eligible for obligation planning.
- Requirements marked `duplicate` must identify `duplicate_of`.
- Requirements marked `conflicting` should identify `conflicts_with`.
- Ambiguous, related, or conflicting requirements must not be silently merged.

JSON example:

```json
{
  "governed_ledger_id": "gov_ledger_001",
  "project_id": "demo_chatbot",
  "atomic_ledger_id": "atomic_ledger_001",
  "requirements": [
    {
      "requirement_id": "req_001",
      "statement": "The bot asks for an order number before providing order status.",
      "requirement_type": "functional",
      "status": "validated",
      "origin": "source_derived",
      "candidate_ids": ["cand_001"],
      "source_refs": [
        {
          "document_id": "doc_001",
          "chunk_id": "chunk_001"
        }
      ]
    }
  ],
  "governance_summary": {
    "validated": 1,
    "duplicate": 0,
    "conflicting": 0,
    "rejected": 0
  }
}
```

## 11. TestObligation

Purpose: Defines a specific testing obligation derived from a governed requirement.

Required fields:

- `obligation_id`
- `requirement_id`
- `obligation_type`
- `status`
- `source_refs`

Optional fields:

- `description`
- `coverage_intent`
- `blocked_reason`
- `metadata`

Validation rules:

- `obligation_id` is required.
- `requirement_id` is required.
- `obligation_type` is required.
- `status` must be one of `planned`, `generated`, `covered`, `blocked_missing_data`, `blocked_unclear_requirement`, `skipped_by_policy`, or `rejected`.
- `source_refs` must be inherited from the linked requirement.
- Normal obligations cannot link to rejected requirements.

JSON example:

```json
{
  "obligation_id": "obl_001",
  "requirement_id": "req_001",
  "obligation_type": "positive",
  "status": "planned",
  "description": "Verify order status is not provided before an order number is collected.",
  "source_refs": [
    {
      "document_id": "doc_001",
      "chunk_id": "chunk_001"
    }
  ]
}
```

Purpose: Groups planned obligations for test generation.

Required fields:

- `obligation_ledger_id`

Optional fields:

- `coverage_policy_snapshot`
- `metadata`

Validation rules:

- Obligation IDs must be unique.
- Every normal obligation must reference a known governed requirement.

```json
  "obligations": [
    {
      "obligation_id": "obl_001",
      "requirement_id": "req_001",

      "status": "planned",
      "source_refs": [
        {
          "document_id": "doc_001",
          "chunk_id": "chunk_001"
        }
      ]
    }
  ]
}
```

## 13. ConversationTurn

Purpose: Represents one user, bot, or system turn inside a chatbot test case.

Required fields:

- `turn_id`
- `speaker`
- `text`

Optional fields:

- `expected_intent`
- `expected_state`
- `metadata`

Validation rules:

- `speaker` should be one of `user`, `bot`, or `system`.
- `text` cannot be empty.
- Turn IDs must be unique within a test case.

JSON example:

```json
{
  "turn_id": "turn_001",
  "speaker": "user",
  "text": "Where is my order?",
  "expected_intent": "check_order_status"
}
```

## 14. Assertion

Purpose: Defines an expected behavior or outcome for a test case.

Required fields:

- `assertion_id`
- `assertion_type`
- `target`
- `expected`

Optional fields:

- `severity`
- `metadata`

Validation rules:

- `assertion_id` must be unique within a test case.
- `assertion_type` cannot be empty.
- `expected` must be specific enough for a validator or reviewer to evaluate.

JSON example:

```json
{
  "assertion_id": "assert_001",
  "assertion_type": "bot_response_contains_request",
  "target": "bot.final_response",
  "expected": "The bot asks for the order number before providing status."
}
```

## 15. TestCase

Purpose: Represents a draft or validated chatbot test case.

Required fields:

- `test_case_id`
- `title`
- `status`
- `requirement_ids`
- `obligation_ids`
- `turns`
- `assertions`

Optional fields:

- `source_refs`
- `priority`
- `tags`
- `export_eligible`
- `rejection_reasons`
- `metadata`

Validation rules:

- `test_case_id` is required.
- `title` is required.
- `status` must be one of `draft`, `valid`, `needs_review`, `approved`, `rejected`, or `exported`.
- `requirement_ids` is required and cannot be empty.
- `obligation_ids` is required and cannot be empty.
- `source_refs` is optional for draft, `needs_review`, rejected, or otherwise non-exportable tests.
- `source_refs` is required and must be non-empty before a test case can be `valid`, `approved`, `exported`, or included in an `ExecutorExportPackage`.
- A test case without `source_refs` must not be exportable.
- Test cases with unknown `requirement_ids` must be rejected.
- Test cases with unknown `obligation_ids` must be rejected.
- Orphan test cases must be rejected.
- Test cases linked to conflicting requirements are not exportable.

JSON example:

```json
{
  "test_case_id": "tc_001",
  "title": "Order status requires order number",
  "status": "draft",
  "requirement_ids": ["req_001"],
  "obligation_ids": ["obl_001"],
  "source_refs": [
    {
      "document_id": "doc_001",
      "chunk_id": "chunk_001"
    }
  ],
  "turns": [
    {
      "turn_id": "turn_001",
      "speaker": "user",
      "text": "Where is my order?"
    }
  ],
  "assertions": [
    {
      "assertion_id": "assert_001",
      "assertion_type": "bot_response_contains_request",
      "target": "bot.final_response",
      "expected": "The bot asks for the order number before providing status."
    }
  ]
}
```

## 17. ValidatedTestSuite

Purpose: Stores test cases after deterministic validation and export eligibility checks.

Required fields:

- `validated_suite_id`
- `project_id`
- `draft_suite_id`
- `test_cases`
- `validation_summary`

Optional fields:

- `metadata`

Validation rules:

- Orphan test cases must be rejected.
- Tests with unknown requirements or obligations must be rejected.
- Export eligibility must be recorded per test or in validation summary.
- Tests marked `valid`, `approved`, or `exported` must have non-empty `source_refs`.
- Tests without `source_refs` must not be exportable.
- Tests linked to conflicting requirements are not exportable.

JSON example:

```json
{
  "validated_suite_id": "validated_suite_001",
  "project_id": "demo_chatbot",
  "draft_suite_id": "draft_suite_001",

    {

        {

        }

    }
  ],

    "valid": 1,
```

Purpose: Describes the executor-ready export output.

Required fields:

- `export_package_id`
- `project_id`
- `validated_suite_id`
- `exported_test_case_ids`
- `format`
- `output_paths`
- `eligibility_summary`

Optional fields:

```json
    "excluded": 0
  }
}
```

## 21. SkillDefinition

Purpose: Defines a runtime skill that the Skill Runtime may execute.

Required fields:

- `skill_id`
- `name`
- `version`
- `input_contract`
- `output_contract`
- `entrypoint`

Optional fields:

- `description`
- `timeout_seconds`
- `metadata`

Validation rules:

- Skill definitions must declare input and output contracts.
- Runtime skills may perform LLM reasoning, but must not own deterministic pipeline state.
- Components must invoke skills only through the Skill Runtime.

JSON example:

```json
{
  "skill_id": "requirement_extraction_v1",
  "name": "Requirement Extraction",
  "version": "1.0.0",
  "input_contract": "SourcePackage",
  "output_contract": "CandidateRequirementPackage",
  "entrypoint": "skills/requirement_extraction_v1"
}
```

## 22. SkillRunRecord

Purpose: Records one Skill Runtime execution for auditability.

Required fields:

- `skill_run_id`
- `skill_id`
- `status`
- `input_artifact_paths`
- `output_artifact_paths`

Optional fields:

- `started_at`
- `completed_at`
- `error`
- `metadata`

Validation rules:

- `status` should be one of `planned`, `running`, `succeeded`, or `failed`.
- Input and output artifacts must be validated against the skill definition contracts.
- Failed runs must include an `error`.

JSON example:

```json
{
  "skill_run_id": "skill_run_001",
  "skill_id": "requirement_extraction_v1",
  "status": "succeeded",
  "input_artifact_paths": [
    "artifacts/demo_chatbot/run_001/02_source_package/source_package.json"
  ],
  "output_artifact_paths": [
    "artifacts/demo_chatbot/run_001/03_candidate_requirements/candidate_requirement_package.json"
  ]
```

## 23. PipelineRunState

Purpose: Tracks orchestration state across pipeline stages.

Required fields:

- `pipeline_run_id`
- `project_id`
- `run_id`
- `status`
- `current_stage`
- `artifact_paths`

Optional fields:

- `completed_stages`
- `failed_stage`
- `error`
- `created_at`
- `updated_at`
- `metadata`

Validation rules:

- `status` should be one of `not_started`, `running`, `succeeded`, or `failed`.
- `current_stage` must be a known component or pipeline stage.
- Completed stages must not skip required prior stages.
- Artifact paths must use the configured artifact root.

JSON example:

```json
{
  "pipeline_run_id": "pipeline_001",
  "project_id": "demo_chatbot",
  "run_id": "run_001",
  "status": "running",
  "current_stage": "C07_requirement_extraction",
  "completed_stages": [
    "C03_project_config",
    "C04_document_ingestion",
    "C05_source_ledger",
    "C06_skill_runtime"
  ],
  "artifact_paths": {
    "project_config": "artifacts/demo_chatbot/run_001/00_project_config/project_config.json",
    "source_package": "artifacts/demo_chatbot/run_001/02_source_package/source_package.json"
  }
}
```
